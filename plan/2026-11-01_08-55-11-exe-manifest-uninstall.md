## 当前执行范围：仅 install、update、uninstall

本节取代下方历史方案的实施范围。此前把审查中的恢复需求扩展为独立卸载产品、便携缓存迁移和 MSI 策略补齐，超出了用户要求的最小改动；以后先判断是否直接影响这三个操作，再增加机制。

### 保留的三个操作

| 操作 | 必需改动 | 继续复用 |
|---|---|---|
| `--install` | 从当前包取得完整路径列表，按最终名称安装并记录实际归属；已有安装仅允许同目录重装，不先递归卸载。旧版无清单时保留用户已选的一次覆盖确认。 | 当前安装选项、首装目录选择、UAC、注册项及系统组件安装逻辑；已有安装沿用原目录。 |
| `--update` | 按包列表替换文件并更新归属；保留降级能力。完整同产品包成功后清理旧清单差集；通用包更新定制安装时保留包外旧文件及归属。 | 当前目录、选项、服务状态和系统组件更新逻辑，不重新实现 MSI 的状态保留体系。 |
| `--uninstall` | 仅删除清单中的文件、精确定位的固定生成物及允许清理的空目录；保留未知文件和链接，必要删除失败明确报告。 | 当前系统集成清理及提权入口；文件阶段替换现有整目录删除。 |

更新规则仍为：可信旧集合为 `O`，经过最终 EXE 名映射的新包集合为 `P`。完整替换成功后为 `P`；通用包更新定制安装成功后为 `O ∪ P`。后者不删除 `O − P`，也不新增逐文件来源登记。通用更新可能保留弃用文件，但这些条目继续参与卸载。

### 必需边界

- 只新增安装目录中的 `data/meta/install-manifest.json`。现有根目录 `meta.toml` 保持位置、格式和便携缓存用途，不拿它推断安装归属。
- 普通便携运行、Quick Support、缓存刷新、定制缓存清理及 MSI 路径保持现状。包装器只允许增加为上述安装/更新提供准确包列表所必需的薄接入，不以此为由迁移缓存或重写解包流程。
- 包列表来自合并后的 `BinaryReader.files`（`libs/portable/src/bin_reader.rs:31`、`:45`），不扫描解包目录或安装目录认领文件，也不将 `package_paths` 当成完整列表。保留来源验证和受保护暂存；复用 `src/platform/windows/installer_files.rs:39`，不新增永久第二份包清单或完整安装包缓存。
- 包内路径映射到实际安装名称后再计算集合。通用更新读取经验证的旧定制配置；完整定制包使用自身配置，不能被 `prepare_custom_client_update` 覆盖或删掉新配置。产品、根、架构及 EXE/MSI 归属检查保留，包版本高低不作为拒绝条件。
- 首次安装可选择目录；已有 EXE 安装（含旧版确认迁移）的目标根须经路径/目录身份核验，与可信注册信息中的安装根一致。另选目录在停止服务、写文件或改注册项之前拒绝，不把它当作首装，不把旧清单套到新目录，也不新增目录迁移功能。
- 路径必须是合法相对路径；拒绝 `..`、绝对路径、Windows 路径别名冲突、控制文件覆盖和 symlink/junction/reparse point。检查覆盖根、父目录链和叶子对象；不能以“先检查、后按字符串删除”冒充竞态防护。链接保留并报告，不遍历链接目标。
- RuntimeBroker、固定快捷方式继续按可信根与已有固定名称定位，不增加登记表；不存在视为已处理，其他必要操作错误不吞掉。
- 安装记录原子写入、必要的操作互斥和单条在途发布信息只服务于文件归属正确性；保留普通失败时的核验与错误传播，不扩展为跨文件回滚、自动修复或后台恢复系统。记录缺失、不可读、损坏或格式不兼容时，`--uninstall` 在任何变更前报错，不能当作空清单或转用旧递归卸载。
- 旧版首次迁移确认绑定本次包、根及覆盖范围；取消或静默缺少显式授权时，在停止服务/变更目标文件前退出。继续使用已定的迁移选项，不另加配置页面、FFI 接口或长期授权记录。
- 首次迁移中断后，现有清单只临时保留尚未发布目标的已确认对象身份和目标摘要；重试仅复用这些许可，不再提示确认，也不把未发布文件计入卸载归属。单项发布完成即消费许可，卸载取消剩余许可；成功记录不保留此字段。

### 卸载执行方式的最小验证

实施前的 master `94c321d05` 中，`get_uninstall` 在 `src/platform/windows.rs:1903` 递归删除安装目录，`run_cmds` 已有受保护提权及等待逻辑（`src/platform/windows/installer_handoff.rs:100`）。这些基线位置说明原接入点；当前 EXE 递归删除分支已移除。

1. 在停止进程/服务、清理系统组件或修改文件/注册项之前，读取并验证产品、安装根和清单。真正旧版无清单也拒绝直接卸载；须先按既定 `--install` 显式确认迁移，未接管的包外历史文件仍保留，不扫描补出清单。
2. 系统组件清理仍在应用文件删除前通过原有专用逻辑执行，不把这些实现复制进新卸载程序。卸载注册项（含 `InstallLocation`）及清单保留至受管文件和必要系统组件均清理成功；不能照搬 `src/platform/windows.rs:1901` 提前删除注册项的顺序，否则自定义目录会失去 `src/platform/windows.rs:1495` 使用的定位信息。
3. 验证既有执行链能否完成运行中 EXE/DLL 的退出后清理、目录链约束及真实结果报告；不能只把 `rd /s` 换成一批 `del`，也不能把启动清理进程当作卸载成功。
4. 若复用需要一个额外执行载体，只限定为执行清单文件操作的最小辅助程序；先记录为何现有入口无法承担，再单列必要源码/构建接入。不默认新增安装器框架、ARP 入口、永久恢复缓存或完整应用副本。
5. 采用用户已确认的完整安装包重试方案。部分卸载失败后可能无法从已安装应用再次启动；卸载注册信息、清单及未完成信息必须保留。重试需要支持本清单格式、产品匹配的完整安装包（定制安装须有匹配的定制包），重新执行 `--uninstall` 只处理原清单范围，不扫描认领残留。该限制必须明确告知，不能声称无需源包恢复。

仅在上述文件和必要系统组件清理成功后，才删除清单、卸载注册项并收尾空目录。最终控制信息清理不是跨资源事务；此时失败应报告具体控制残留，不假报全部完成，也不以缺失清单为由重新执行普通卸载。不新增专用收尾状态机。

## 能否直接使用 meta.toml

**不能将现有内容原样作为完整的卸载清单。可以扩展复用，但本计划建议保留其缓存职责，另建受保护的安装记录。**

| 原因 | 依据与后果 |
|---|---|
| 文件集合不完整 | `main.rs:185` 传给写入函数的是 `package_paths`，不是全部 `reader.files`；通用 DLL、资源等可能没有记录。 |
| 生命周期不同 | `main.rs:183`、`:190` 会清理缓存并重写元数据；安装归属记录必须跨更新保留，不能随便携缓存重建。 |
| 包文件不等于安装结果 | 主 EXE 可能改名，复制也可能失败。RuntimeBroker 和固定快捷方式由独立的确定性规则清理，无须为它们增加登记；包文件仍须记录实际安装结果。 |
| 信任等级不同 | `main.rs:89` 明确说明文件位于用户可写目录；复制到受保护位置不能证明此前内容可信。 |
| 名称不代表标准 TOML | `main.rs:68` 输出原始的重复 `file = <path>` 行。带文件条目的样本经标准 TOML 解析器验证失败；不能直接换成 TOML 反序列化器。 |
| 已有特殊消费者 | MSI 定制客户端的 `remove_meta_toml_cmd` 会删除同名文件；迁移位置后须同时识别旧/新路径，不能误删 EXE 安装记录。 |

如果明确选择复用文件名，仍须定义版本和角色、补充全量文件、区分包清单与实际安装记录、调整全部读写/清理路径、处理旧格式，并保护来源及原子更新。不能直接扩大现有 `file = ` 条目的含义，否则会改变定制资源清理逻辑。

因此默认方案是：

- 现有 `meta.toml` 的格式和便携缓存语义保持不变，Windows 上的位置迁移到解包根目录的 `data/meta/meta.toml`。
- 完整包清单由最终 `BinaryReader.files` 派生，作为安装输入；不从运行后的目录扫描反推。
- `install-manifest.json` 由安装程序生成，记录实际归属，放在安装根目录的 `data/meta/install-manifest.json`，保护记录及其所在目录链。
- 两者不是并行维护的两份文件名单：一个管理解包缓存，另一个记录安装结果；实际包文件集合仍只有 payload 这一来源。
- 可复用现有元数据解析经验和路径检查思路，但当前 `resolve_within` 只有词法约束，不能作为重解析点及竞态防护的完整实现。

## data/meta 目录与旧位置迁移

`data/meta/` 相对于当前应用的解包根目录或安装根目录，不相对于进程工作目录；用户配置目录不迁入这里。两个根目录分别管理，不因相对路径相同就共享权限或状态。

| 位置 | 内容 | 写入者与生命周期 |
|---|---|---|
| `<portable-root>/data/meta/meta.toml` | 原有时间戳和定制资源缓存记录 | 便携包装器；随解包缓存刷新，仅影响便携目录。 |
| `<install-root>/data/meta/install-manifest.json` | 系统安装文件归属及操作状态 | 经过验证的安装/更新/卸载路径；跨版本保留，普通运行不写。 |
| 包内或受保护的临时交接位置 | 本次完整 payload 清单 | 从经过验证的最终包派生，消费后清理；默认不新增永久 `package-manifest.json`。 |

- `data/meta/` 是控制元数据保留区，根目录 `meta.toml` 是旧控制文件位置。通用包及定制包不能把这些位置作为普通 payload 覆盖；打包和运行时入口都检查冲突并明确报错。
- EXE 安装/更新不从便携目录复制 `data/meta/`；不能用目录镜像、替换整个 `data/` 或递归删除抹掉安装记录。Flutter 资源和控制元数据各自处理。
- 安装记录采用同目录临时文件写入并原子发布；临时文件不是第二份长期清单。失败必须报告，不能靠截断重写掩盖损坏。
- 仅在目录身份、权限和重解析点检查通过后创建/读取元数据；移动到子目录本身不增加可信度。
- 开始菜单、桌面等外部根由可信系统目录解析；固定快捷方式按产品名和既有规则定位，不逐项登记，也不允许清单指定任意外部路径。

迁移是明确的旧格式兼容步骤，不是读取失败时的静默回退：

1. 新位置不存在、旧根目录 `meta.toml` 存在且符合本应用旧缓存格式时，读取旧缓存信息，安全创建新位置并原子写入；确认成功后仅删除已识别的旧元数据文件，记录迁移结果。
2. 新位置已存在且有效时，以它为准；不合并两份缓存历史。确认旧文件是遗留缓存后再精确清理；未知同名文件不覆盖、不删除，并明确报告冲突。
3. 新位置不可读或损坏时明确报错，不通过旧文件假报读取成功。迁移失败保留旧文件并报告；安装归属不得由任一便携缓存文件推断。
4. 新版本只写新位置。旧版本再次运行可能重建根目录文件；不增加双写、时间戳仲裁或复杂降级协调。非 Windows 位置保持原样。
5. `remove_meta_toml_cmd` 对定制 MSI 的兼容清理仅涉及根目录 `meta.toml` 和 `data/meta/meta.toml`；新路径须通过同样的目录链安全检查。不能删除 `data/meta/` 整个目录或 `install-manifest.json`。

正式安装根目录也可能因旧 `XCOPY` 留有缓存 `meta.toml`。确认历史来源后，由安装器将它迁到该安装根的 `data/meta/meta.toml`，作为已知控制文件单独清理，不登记为包文件；普通运行不更新它，也不据此补出旧安装文件归属。来源不明的同名文件保留并报告，不能只为整理目录而删除。

## 建议的数据与操作边界

- 安装记录包含 `schema_version`、产品/安装身份、包版本、操作状态、已取得归属的包文件和实际创建的目录；仅发布文件期间可带一条 `pending_file`，内容见下文。身份由可信包、实际根和系统注册信息交叉验证，记录不能自我授权。包版本用于记录，不作高低准入检查；清单格式版本另行校验。
- 安装根目录、开始菜单、桌面等由安装上下文/可信系统目录解析；记录内不允许任意绝对路径或命令。
- 系统安装记录只在安装/更新路径创建。正常便携运行及其缓存不取得系统文件归属。
- 完整包清单必须覆盖通用资源、定制覆盖和最终 EXE 名；RuntimeBroker、固定快捷方式等使用下述已知生成物规则，不加入逐文件归属记录。
- 复制与卸载使用同一归属模型。已有未知同名文件不能自动接管；旧版迁移仅在用户明确确认本次包覆盖范围后允许替换，且替换实际发布成功后才取得新文件归属。
- 更新先保留旧记录；新文件写入和旧文件清理的失败不得丢失历史归属。记录原子更新，普通失败明确上报；不宣称具备 MSI 级跨文件事务回滚。
- 预检身份、根目录、记录和路径，并完整准备及验证本次包、检查空间和必要访问权限后，才停止旧服务或开始替换。预检不能保证后续 IO 必然成功。删除失败保留恢复信息；不能先删除记录/卸载注册项再假报成功。
- 卸载只删除已登记包文件、按确定性规则定位的已知生成物及本产品的空目录，保留用户数据和其他未知文件。独立卸载入口及必要控制信息保留到最终收尾，顺序见卸载流程。

### 已知生成物直接清理

- 采用代码内固定规则：受信任的安装根 + `win_topmost_window::INJECTED_PROCESS_EXE`，以及可信系统目录 + 已有产品快捷方式名。依据 `src/platform/windows.rs:1522`、`:1905` 和 MSI 的 `res/msi/CustomActions/CustomActions.cpp:209`，这些位置可直接确定，不需要额外保存“已创建”标记或列表。
- 卸载时直接尝试打开并删除这些精确路径；文件不存在属于正常情况。权限、占用、路径链或对象类型异常必须返回明确错误，不能把“尝试删除”实现为忽略所有失败。
- 同样拒绝 `..`、路径逃逸以及非预期 symlink/junction/reparse point，并处理路径检查与操作间的竞态；不扫描磁盘、不用通配符搜索 `RuntimeBroker*`、不删除系统原版 RuntimeBroker。
- 安装时预检这些保留目标与 payload/未知现有文件的冲突；不是单凭磁盘上任意相似名称认领文件。固定产品快捷方式目录只在清理指定快捷方式后非递归删除，未知内容保留。
- 更新、同版本重装及降级按下文完整替换/通用更新规则处理包文件集合；已知生成物按本次需要创建或精确移除，不混入包文件差集。重复执行删除仍安全，失败可按同一规则重试，不需要生成物恢复日志。
- 首版不新增动态命名的生成物。若以后确有无法确定路径的资源，再在该功能范围内决定最小记录方式，不提前搭建通用登记框架。

### 清单交接：包装器退出前完成

1. 包装器从最终 `BinaryReader.files` 派生一次性包描述：发行包来源身份/架构、包内 EXE 名、规范化路径及每个解压后文件的 SHA-256，并携带实际解析得到的定制 payload 信息。摘要来自包内数据，不来自已经运行过的缓存目录；现有 MD5 不承担来源认证。包内路径与最终安装路径的映射按下文更新类型确定，不将通用包装器中的产品名直接当作定制安装的身份。
2. 启动应用时通过仅供该子进程继承的只读通道传递描述，接收进程在初始化时读取并持有只读安装上下文。通道不是公开命名服务，不从可编辑旁置文件或普通环境变量接受清单内容；`RUSTDESK_APPNAME` 保留原用途。
3. 子进程取得完整描述的只读句柄/内容后，交接介质的生命周期须独立于包装器；包装器此时即可退出，不等待应用退出来保活。稍后点击安装使用已接收上下文，即使原包装器移动/删除也不需要重新定位它。上下文不得转交给来源不同的已有实例，安装请求留在持有该包上下文的进程。
4. 安装前只暂存描述中的文件，并逐项核对 SHA-256；缓存被其他版本覆盖、源文件缺失或摘要不符时，在停止服务/修改安装目录前报错。通用更新保留的旧文件不冒充新包输入，不从旧目录复制后补算包摘要。提权消费的是已验证并受保护的暂存文件和描述，不能再回读用户可写缓存。复用 `installer_files.rs:39` 的校验暂存和现有提权交接，不把暂存保护误当作包来源认证。
5. 信任起点是用户实际启动的安装包及其运行进程；自动更新继续沿用既有包验证。此协议防止旁置清单及缓存替换，不另行建立发布签名体系，也不宣称能抵御已控制应用进程的攻击者。
6. 裸应用 EXE/脱离包装器的新进程没有此上下文时，普通便携运行保持可用；新清单安装要求从完整包装器重新发起并给出明确提示。不能扫描目录补出包清单，也不能静默走旧的整目录复制。已安装应用的卸载使用安装记录，不要求原包装器在场。

不新增永久包清单、安装包缓存或常驻交接服务。继承通道与上下文的具体封装在功能模块内实现，CLI/UI 只作薄接入；描述/文件完整性和受保护暂存是接入运行流程前的验收门槛。

### 单文件发布与普通失败

- 使用 `data/meta/` 下固定的受保护暂存槽，逐个文件完整写入、刷新并验证内容，再发布至最终路径；不直接截断目标文件。暂存槽属于明确的安装控制产物，按精确路径和对象类型处理，不扫描临时目录。
- 复制失败时目标不变，按已持有句柄清理暂存文件；清理也失败则同时报告两项错误，保留该固定槽供显式重试处理。没有把半成品当作未知包文件留在最终路径。
- 发布前原子写入一条 `pending_file`：目标相对路径、暂存对象的文件身份与内容摘要，以及目标原本是否受管。迁移覆盖还须绑定已确认的原目标对象；不能在确认后换成另一个文件。写入待处理记录失败则禁止发布目标。
- 原子发布后才把目标加入已受管集合并清除 `pending_file`。这次记录写入失败时停止后续文件操作；先前持久化的待处理记录仍证明本次发布的对象，不需要扫描或重新认领未知文件。
- 重试先区分已发布与仍暂存：目标匹配暂存对象的身份/内容则完成登记；对象仍在暂存槽且原目标符合预期时，安装/更新可继续发布，卸载只取消并精确清理暂存项；非预期对象保留并报告冲突。卸载时两处路径均已不存在可清除此项。未发布的迁移覆盖不会使原目标变成可卸载文件。
- 一次只允许一条待处理记录，解决后才处理下一项。它不是 RuntimeBroker 等生成物的登记，也不是跨文件回滚日志。删除仍采用“先精确删除、再移除归属”；记录更新失败后重试可识别文件已不存在。

### 旧版迁移：显式确认后仅接管本次覆盖范围

- 仅对可信注册信息确认的同一 EXE 产品和安装根提供迁移；MSI 不进入此分支。新流程在现有注册项写入 `InstallManifestVersion` 能力标记：已声明支持清单却丢失记录，与真正旧版无记录区别处理；损坏/未知格式也不能自动降格为旧版迁移。
- 对真正旧版无记录的安装，列出目标包路径与现存文件的交集，由用户一次性确认本次覆盖范围；用户已明确选择此策略。确认绑定本次包、根目录和覆盖集合，取消发生在停止进程及写入安装文件之前。
- 静默迁移要求显式选项（拟定 `--migrate-legacy-installation`）；普通 `--silent-install` 不代表迁移确认。缺少该选项返回可操作的迁移提示，不自动忽略冲突。
- `--update` 同样不能代替首次迁移确认。无交互更新遇到真正旧版无清单时，须在停止进程/服务及目标文件变更前返回需要迁移的错误，提示通过完整包的 `--install` 完成一次确认；无人值守迁移复用前述显式选项，不因自动更新身份而默认授权覆盖。迁移完成后的普通更新不重复确认。
- 初始受管集合为空，按上述发布协议写入目标包；仅实际发布的新包文件取得归属。旧目录中目标包以外的文件保持原样，不执行历史文件差集删除，不声称恢复了旧版完整清单。
- 迁移完成后正常使用新清单；中断后已登记/待处理文件按记录恢复，剩余未知覆盖如重新发起操作仍需确认，不能保存一个无限期接管未知文件的许可。
- 旧版无清单的直接卸载不伪造空清单，也不调用递归删除作为兼容分支；需要先用完整安装包完成上述确认迁移，再按清单卸载。明确说明未被接管的旧版遗留文件可能保留。
- 允许历史安装器降级的决定不变。已识别的过期清单须显式核对、报告并选择迁移/修复，不能继续把它当作当前完整包清单；本方案不能使未修改的旧安装器遵守新记录协议。

## 安装、更新与卸载流程

以下是拟实施的明确流程，当前代码尚未实现。同一产品的安装、更新、重装和卸载共用产品级操作锁；锁覆盖预检、确认后的复核、文件发布及收尾，并在进程退出时释放。不能仅锁某个目录而让不同目录同时修改同名服务/注册项，也不将提权 handoff gate 当作操作互斥；竞争操作明确报忙，不自动重试。

安装记录使用最小状态集合 `ready`、`installing`、`updating`、`uninstalling`。开始变更前先持久化相应状态；全部必要步骤成功后才标记 `ready` 或完成卸载。普通错误/进程中断留下未完成状态，重试时明确识别，不假设此前已经完成或回滚。

### 两个入口的分工

当前代码中，`--install` 的 `install_me` 先拼接 `get_uninstall(false, false)`，包含整目录删除，再复制新文件（`src/platform/windows.rs:1634`、`:1778`、`:1903`）；`--update` 则明确保留旧目录并覆盖复制（`src/platform/windows.rs:3624`、`:3642`）。这些是现状，不是新清单流程应继续继承的文件删除策略。

新流程先识别安装器归属，再按清单状态分流；下表只适用于 EXE 安装。`--install` 继续拒绝覆盖 MSI，`--update` 的既有 MSI 分支保持原样，不套用 EXE 清单或迁移门槛。

| 已有 EXE 安装状态 | `--install` | `--update` |
|---|---|---|
| 没有已有安装 | 执行首次安装 | 报告未安装，不隐式转为首次安装 |
| 有可信、兼容的安装记录 | 按本次安装选项同目录重装，文件按下述替换流程处理 | 保留已有目录、选项及运行状态，文件按同一替换流程处理 |
| 真正旧版，无安装记录 | 一次确认后只替换本次包路径并建立归属；包外历史文件保留 | 按迁移节处理首次授权；未获授权前停止，不清空目录或静默认领 |
| 新流程记录丢失、损坏、未知格式或已识别过期 | 明确报告并要求核验/修复，不当作旧版无记录 | 同左 |

- 安装更低版本不会改变上述分支；升级、降级和同版本重装采用同一文件规则。较低包版本与不兼容清单格式是不同问题。
- `--install` 不先调用现有整目录卸载或旧版卸载器。服务、注册项、快捷方式等仅复用本次安装所需的专用步骤；文件阶段保留清单和可重试入口，先发布目标包，再删除旧清单中目标包不再需要的文件。不先移除整份记录或进入卸载收尾模式。
- 保留两个入口的选项及系统集成职责，不把 `install_me` 直接改成调用 `update_me`；仅复用必要的清单文件操作。`--update` 不重置安装选项或执行完整卸载，也不默认新增未安装的可选组件。

### 首次安装

1. 完整准备并验证包与文件清单、产品身份、安装选项、目标根和路径链；检查空间及必要权限。区分首次安装、已有 EXE 安装和 MSI；检查未归属文件的同名冲突及源/目标重叠。预检失败不改目标文件或注册项。
2. 创建受保护的目标目录及 `data/meta/`，写入 `installing` 记录，登记本次实际创建的目录。
3. 按单文件发布协议先写入独立卸载入口，再处理其余包文件；使用最终目标名。任何文件或记录失败都停止后续发布，保留可核验的待处理信息，不扫描目录补出归属。注册项尚未发布的部分安装可从已写入的独立入口清理；入口自身写入失败时，尚未开始其他包文件的发布。
4. 按现有选项在固定位置创建 RuntimeBroker、快捷方式等生成物，不逐项登记；服务、驱动、证书仍由现有专用逻辑完成并检查必要结果。
5. 注册独立卸载入口并发布安装版本、清单能力标记，最后原子提交 `ready` 记录；此后才报告安装成功。独立入口随包提供、按普通包文件登记，不能在未验证它可独立运行时改写卸载注册项。

已有 EXE 的同目录重装采用下面的文件替换流程；入口职责仍按上表区分。首版不自动迁移已有安装目录，不能将旧记录直接套用到用户另选的目录。

### 通用包更新定制安装与完整包替换

当前定制更新先暂存旧 `custom.txt`（`src/updater.rs:314`），新进程加载后删除解包目录中的副本（`src/platform/windows.rs:2137`、`:2140`），旧安装目录里的原文件依靠覆盖式更新保留。已签名的配置可决定产品名（`src/common.rs:2603`、`:2614`），安装时还会按该名称映射主 EXE（`src/platform/windows.rs:1535`）。因此通用发行包不能代表定制安装的完整目标文件集合。

以 `O` 表示可信旧受管文件集合，`P` 表示新包路径经过最终目标名映射后的集合；以下结果仅在发布/清理全部成功后成立，普通失败仍按单文件协议保留实际归属。

| 本次操作 | 保留与删除规则 | 成功后的受管集合 |
|---|---|---|
| 通用包安装/更新非定制产品，或同一产品的完整定制包替换 | 发布 `P`，再删除 `O − P` | `P` |
| `--update` 使用通用包更新已有定制安装 | 发布 `P`，保留 `O − P` 中全部已有文件及归属，不执行旧文件差集删除 | `O ∪ P` |

- 第二种操作沿用已有覆盖更新的文件语义：`P` 中同名文件正常更新；新包未携带的 `custom.txt`、定制资源及其他旧受管文件保留。未受管文件仍不认领。保留的条目继续参与重试及卸载，不能只保留文件却从清单丢掉它们。
- 不新增逐文件“通用/定制来源”字段或第二份长期清单。代价是通用更新可能保留已弃用的旧通用文件；后续同产品完整定制包替换可按完整差集清理，卸载仍处理全部已登记文件。这不是损坏清单时的回退。
- 操作类型须在改动源缓存、停止服务或修改安装目录前确定：结合包中实际定制 payload/经验证的包内配置，以及旧安装的可信身份和经验证配置。不能凭文件名、缺少 `custom.txt` 或产品同名就推断。无法确认则明确报错；无旧清单仍先遵守既定迁移确认，不因使用通用包而绕过。
- 完整定制包使用包内经验证的配置，不能执行会用旧暂存配置覆盖并删除新包 `custom.txt` 的准备步骤。通用更新复用旧配置的签名验证，并与可信注册信息/旧记录交叉核验目标产品；发行包来源身份与安装产品身份分别验证，不放宽任意其他产品包的准入。
- 通用更新在上述核验后，将包内主 EXE 唯一映射至已有产品的最终 EXE 名，再计算 `P`；摘要仍对应原始包内字节。映射冲突或指向未归属目标按既有预检规则报错。记录只保存实际最终路径，不额外留下通用 EXE 名的副本。`--install` 不隐式承担去除定制的转换，未定义转换明确拒绝。

### 清单文件替换：更新与同目录重装

1. 取得可信旧安装记录及完整准备好的目标包，先确定上表中的操作类型及最终路径映射，再核验发行包来源、目标产品、安装器类型、范围、架构、根和清单格式；目标包版本较低也允许执行，没有旧记录的历史安装进入已明确的迁移策略，不假装首次安装。
2. 按上表计算保留/替换、新增、待移除的包文件集合；完整替换才删除 `O − P`，通用包更新定制安装时不删除旧集合差集。不枚举磁盘寻找“多余文件”；升级、降级和同版本操作按同一包类型规则执行，固定生成物单独处理。
3. 停止前读取安装选项及服务/打印机实际状态，按下节优先级确定本次行为。持久化 `updating`，保留全部旧归属，再停止并确认需要停止的进程/服务已经退出；失败不能继续删除占用文件。
4. 按单文件发布协议处理新增/替换文件、最终 EXE 名和必要生成物；待处理项未解决不得开始下一项。安装记录始终由安装器管理，不能被包内文件覆盖。
5. 新内容写入成功后删除待移除的所属文件。只有删除成功或确认已不存在，才移除对应归属；任何失败保留条目和未完成状态，不提交成功版本。
6. 必要集成与原有服务状态恢复成功后，提交新版本信息及 `ready` 记录；通用包更新定制安装时一并保留旧条目的归属，不能只写入 `P`。保留用户文件；不把部分更新描述为自动回滚到旧版本。

降级到尚不认识新清单的历史安装器时，不能承诺其后续安装/卸载会遵守本方案；不因此阻止降级，也不增加对旧程序的拦截。旧安装器操作后留下的新清单可能已经过期，再进入新流程时须核实实际安装信息，不能直接信任旧 `ready` 状态或将缓存元数据当作完整归属。

### 卸载

1. 从随包安装的独立入口（拟定 `<install-root>/uninstall.exe`）执行；它仅依赖系统运行环境，不依赖应用 EXE、`librustdesk.dll` 或 Flutter 资源。验证产品、根、记录及操作锁；旧版无记录按迁移规则处理，损坏/未知格式明确报错。
2. 先按卸载语义核验/解决 `pending_file`，再持久化 `uninstalling`；停止应用进程/服务及移除必要系统集成。独立入口直接复用必要的专用清理逻辑并识别“已经移除”，不能在重试时调用已删除的应用 EXE；也不能被按应用名称结束进程的命令一并杀死。
3. 删除受管包文件，但始终保留独立入口及控制记录；固定生成物按精确规则清理。每次删除成功后更新剩余集合，缺失视为已完成；其他异常停止并报告。应用 EXE/DLL 可删除，因为重试入口不依赖它们。
4. 普通失败保留独立入口、清单和指向该入口的卸载注册项。用户可再次运行同一个入口继续剩余工作，不需要原安装包、已删除的主程序或另外恢复 Flutter DLL。
5. 仅剩独立入口且系统集成清理成功时，先将现有卸载命令切换为该入口的收尾模式，再清理安装记录、卸载注册项及空目录。切换失败不开始收尾；收尾模式不再删除普通包文件，记录存在时须核实剩余集合仅含自身且无待处理发布项。
6. 独立入口最后退出，由经过验证的系统命令载体完成它的自删除和必要空目录收尾。沿用现有受保护交接/等待方式的可复用部分，不采用固定延时、未保护的 helper 或重启删除队列。

收尾模式只允许清理本产品的记录、自身及已确认的空目录，不因缺少清单就重新开始普通卸载。跨注册表/文件的最后几步仍不是事务：若应用和系统集成已移除、但最终控制文件/自删除失败，必须报告“应用已移除，清理未完成”和准确的重试命令/残留路径，不能假报全部完成或承诺 ARP 一定仍在。只要独立入口尚在就可直接再次运行收尾模式；入口已删除后，仅剩空目录的清理错误按残留报告，不再声称需要应用文件才能重试。

这是为 P1 增加的唯一独立执行产物；复用同一清单及安全文件操作实现，不复制整套应用运行时、不保留完整安装包，也不增加后台清理服务。

### 失败与中断边界

- 普通复制/发布错误由固定暂存槽、单条待处理记录和对象核验处理；失败不丢弃相关记录，未核验对象不自动认领。独立卸载入口的最终收尾错误与普通包文件清理错误分别报告。
- 文件发布、注册表与记录仍不是跨资源事务；断电/强制终止后须重新验证文件身份和内容。文件系统未保留可验证证据时报告无法自动恢复，不以目录扫描、空清单或状态标记代替证明，也不承诺透明恢复。
- 重跑完整安装包可继续已验证的安装/更新；原入口可继续普通卸载，收尾模式只处理控制残留。缺少源包不会妨碍正常卸载，但不能修复缺失的应用内容。已知固定生成物仍不需要登记。

## 必须注意的点

1. **来源验证与写保护不同。** 明确从原始包、最终定制 payload 到提权后读取者的验证链。`ProtectedInstallFile::new` 只保护交接字节，现有 MD5 校验也不能代替来源认证。
2. **限制整个路径链。** 拒绝 `..`、绝对/盘符相对/UNC/设备路径、ADS、保留设备名及 Windows 歧义命名；检查安装根与中间目录。字符串前缀或先 canonicalize 再按路径删除不足以防竞态。
3. **链接策略明确。** 首版按现有 payload 的普通文件模型实现。非预期 symlink/junction/reparse point 明确报错，不跟随目标；以后若支持包内链接，须单独定义删除链接本身的语义。硬链接不属于重解析点，安装覆盖也不能原位破坏外部共享目标。
4. **不扫描推断所有权。** 包文件按清单清理，已知固定生成物按代码规则清理；其他未登记文件、日志、用户配置及非空目录保留。文件已不存在与权限错误/占用/类型变化分开处理；失败不转成递归删除。
5. **新旧安装区分。** 新安装无旧记录正常；清单能力标记、可信注册信息与记录共同区分旧版迁移和新流程损坏。迁移确认只授权当前包的覆盖，不产生历史文件归属，不将缺损/未知格式当作空清单。
6. **重装和源/目标重叠。** `install_me` 已调用卸载逻辑；不能先删旧目录再读取记录，也不能清理仍作为本次源目录的解包位置。
7. **运行中 EXE 与失败恢复。** 独立入口必须在主程序及 Flutter DLL 已删除后仍可启动；不能从用户可写位置加载依赖。验证普通重试、收尾模式和入口自删除；最终控制清理失败须报告残留，不自动加入重启删除策略。
8. **保护便携及 MSI。** 两种根目录的元数据不能互相复制。定制 MSI 仅补旧/新缓存位置的精确清理兼容，不能清空 `data/meta/`；不要全局替换 `copy_raw_cmd` 或为共享调用者增加占位参数。
9. **控制新增状态。** 审查修复仅增加一条在途发布记录、一个清单能力标记和卸载命令的收尾模式；分别解决普通写入失败、丢失清单误判旧版、删除应用后无法收尾的问题。不扩展为历史日志、完整回滚、后台扫描或自动重试机制。
10. **兼容性不凭推测。** 验证现有 Windows 7 要求、发布架构和实际 Rust 工具链。新库未验证前不进入关键文件操作路径，不引入 PowerShell 依赖。
